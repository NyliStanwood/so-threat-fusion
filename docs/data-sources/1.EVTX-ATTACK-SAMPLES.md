## Overview

A curated collection of ~250 real Windows Event Log (`.evtx`) files, each captured during the execution of a specific MITRE ATT&CK technique. Every file is a self-contained artifact — load it, and you have exactly the Windows events that technique produces, nothing more.

**Why this matters for this project:**

Security Onion is built around network telemetry (Zeek, Suricata). Windows host events require a separate ingestion path. EVTX-ATTACK-SAMPLES provides ready-made ground truth for the host-visibility side of the fusion engine — you know exactly which ATT&CK technique the events represent, so fusion output can be scored against a known answer.

## EVTX Format — Technical Details

EVTX (Windows XML Event Log) is the binary log format used by Windows since Vista. It replaced the older `.evt` format.

| Property | Detail |
|---|---|
| Binary format | Structured binary chunks, not plain XML |
| Encoding | Each event record is XML under the hood — parsers convert to XML/JSON |
| Channels | Security, System, Application, PowerShell/Operational, Sysmon |
| Key fields | `EventID`, `TimeCreated`, `Computer`, `Channel`, `EventData` |

**EventIDs you will encounter frequently:**

| EventID | Channel | What it records |
|---|---|---|
| 4624 / 4625 | Security | Logon success / failure |
| 4688 | Security | Process creation (requires audit policy) |
| 4698 / 4702 | Security | Scheduled task created / modified |
| 1102 | Security | Audit log cleared |
| 7045 | System | New service installed |
| 1 / 3 / 10 | Sysmon | Process create / network conn / process access |
| 4104 | PowerShell | Script block logging |

## Ingestion into Security Onion

SO does not natively ingest `.evtx` files directly — it expects a live Elastic Agent or Winlogbeat shipper. To replay EVTX files into SO you need to convert them first.

### Path 1 — python-evtx → JSON → Elasticsearch API (recommended for this project)

Parse the EVTX to JSON, then POST directly to SO's Elasticsearch into a dedicated index.

```bash
pip install evtx          # python-evtx library
pip install elasticsearch # elasticsearch-py client
```

```python
from evtx import PyEvtxParser
import json

parser = PyEvtxParser("T1003_LSASS_Memory.evtx")
for record in parser.records_json():
    event = json.loads(record["data"])
    # POST to SO Elasticsearch: index = logs-windows-lab
```

This is the most direct path for Phase L2 (lab data injection) and gives you full control over the index name and metadata fields.

### Path 2 — Winlogbeat on a Windows VM

Install Winlogbeat on a Windows VM, point it at the `.evtx` file path, configure output to SO's Logstash (port 5044). Events arrive ECS-normalized, same format as live Windows hosts.

```yaml
# winlogbeat.yml snippet
winlogbeat.event_logs:
  - name: "C:/path/to/T1003_LSASS.evtx"
    no_more_events: stop

output.logstash:
  hosts: ["10.0.2.3:5044"]
```

Best option if you want the events to look identical to real Elastic Agent telemetry inside SO.

### Path 3 — Chainsaw / Hayabusa for offline analysis

Not an ingestion path — these tools parse EVTX locally and apply Sigma/YARA-L detection rules. Useful for:
- Verifying what an EVTX file actually contains before ingesting
- Pre-labeling events with matched Sigma rule names (becomes a ground truth tag)

```bash
# Chainsaw: detect ATT&CK techniques in a folder of EVTX files
chainsaw hunt EVTX-ATTACK-SAMPLES/ --sigma rules/ --mapping mappings/sigma-event-logs-all.yml
```

## Workflow for This Project (Phase L2 / Phase 5)

```
EVTX file (known technique T1003)
        ↓ python-evtx
JSON events
        ↓ elasticsearch-py
SO Elasticsearch (index: logs-windows-lab)
        ↓ fusion_engine.py queries + correlates
Fused cluster with ATT&CK tag
        ↓ compare
Ground truth label (T1003 from filename)
        → coverage delta, false positive rate
```

The filename is the label. If the fusion engine tags the cluster as T1003, it's a hit. If it misses or mislabels, that's a gap — exactly what the evaluation chapter measures.

## Gotchas

- **Timestamps are original capture time** — events will have dates from whenever sbousseaden ran the technique (2018–2022). When injecting into SO, either accept the historical timestamps or rewrite `TimeCreated` to now. Historical timestamps break time-window correlation unless you normalize them.
- **No network telemetry included** — these are host events only. Lateral movement techniques will have host-side artifacts but no Zeek/Suricata network events. For full fusion scenarios you need to pair with a network PCAP (e.g. from PCAP-ATTACK or a live Atomic Red Team run).
- **Some files require Sysmon** — techniques captured with Sysmon logging enabled (EventIDs 1, 3, 10, etc.) won't have equivalent events in a standard Windows Security log. Know which channel each file uses before ingesting.
- **Windows-only events** — not useful for Linux host telemetry scenarios.
